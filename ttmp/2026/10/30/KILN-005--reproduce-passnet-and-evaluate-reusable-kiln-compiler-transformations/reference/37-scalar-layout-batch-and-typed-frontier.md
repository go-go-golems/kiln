# Scalar and layout batch; typed-input frontier

## Batch scope

The first new coverage batch adds source bindings for `torch.square`, functional `leaky_relu`, `hardsigmoid`, `hardswish`, and tensor `expand_as`. These operations reuse Kiln's existing pointwise and static expansion primitives. The scalar bindings live in `integrations/passnet/fx_scalar_ops.py`; `expand_as` is validated and lowered in `fx_import.py`. In-place functional calls still require the importer's existing fresh, single-use ownership proof. The batch does not add a new tensor IR operation or change the existing compiler pipeline.

The operation contracts were checked against the official PyTorch 2.9 documentation for [square](https://docs.pytorch.org/docs/2.9/generated/torch.square.html), [leaky ReLU](https://docs.pytorch.org/docs/2.9/generated/torch.nn.functional.leaky_relu.html), [hard sigmoid](https://docs.pytorch.org/docs/2.9/generated/torch.nn.functional.hardsigmoid.html), [hard swish](https://docs.pytorch.org/docs/2.9/generated/torch.nn.functional.hardswish.html) and [expand_as](https://docs.pytorch.org/docs/2.9/generated/torch.Tensor.expand_as.html), plus the materialized PassNet source calls. All five exact HTML pages are in `sources/pytorch-2-9-scalar-docs-v1.tar.gz`, with URL and SHA256 in `sources/pytorch-2-9-scalar-docs-archive-v1.json`. No PyTorch or PassNet implementation code was copied. The local CPU oracle is PyTorch 2.11.0+cu130; final PassBench replay must check behavior under the pinned 2.9.1 container.

The low-precision scalar path converts to FP32 for the operation and narrows once to the source dtype. It preserves the existing type/shape contract. Hard swish uses `x * clamp(x+3, 0, 6) / 6` rather than only the documented piecewise finite-value formula: local PyTorch returns NaN for negative infinity, and selecting a constant-zero branch would produce zero. The shared scalar oracle covers FP32, FP16, BF16, finite boundaries, signed zero, infinities and NaN. All 51 scalar cases passed PyTorch CPU versus Kiln reference and decomposition, with CUDA emission compiled. This is not a native GPU numerical comparison.

## Measured import gain

The same full 2,060-graph fake-metadata census was run before and after the batch. Importable graphs rose from **1,526 to 1,559** and fully importable tasks from **111 to 116**. Exactly 33 previously blocked graphs became importable; no formerly imported graph regressed. The newly complete families are zero-based tasks **85, 135, 167, 192 and 197**, containing 9, 6, 6, 6 and 6 variants. Every one of the 33 source programs exported and compiled locally with Node26.13.0, target A100, separate contraction and the explicitly bypassed internal synthetic check. The external PassBench evaluator has not yet run on this batch. Its task plan and compilation receipt remain in `sources/`.

## The next deeper compiler boundary

The current census still has 119 first failures at nonfloating placeholders across 18 families. A separate source metadata census found 230 `torch.int64` input declarations and one Boolean declaration among those graphs; many sources contain embedding and index operations. Kiln's dtype width table knows `i64`, but its CUDA scalar path currently treats kernel values as FP32 and its emitted input storage types do not include `i64`. The existing view index maps depend on static output coordinates and cannot express a data-dependent embedding lookup. Simply accepting `torch.int64` in the FX importer would therefore be semantically wrong.

Seventeen other first failures are `get_attr` constants across three families. Their captured tensors range from 49 to 1,050,625 elements and include both `torch.int64` and FP32. They require a representation for static tensor assets or a justified source decomposition; embedding them as scalar literals is not a general solution. A later typed/indexing design should define exact integer loads, dynamic gather indices, constant storage, runtime lifetime and PassBench matching before claiming those families.

This finding changes the next implementation choice. The 33-graph scalar batch was a low-cost extension of existing primitives. The typed-input/constant wave is a cross-layer compiler capability and should be built as one coherent change, with explicit index-range and alias contracts, rather than a collection of import-only exceptions. The ongoing 111-task GPU run uses a frozen pre-batch snapshot and is unaffected by these local source changes.
