# kiln-perf: the CUDA runner in a container

`kiln-perf` holds what Kiln's CUDA side needs on a GPU host and nothing else. The host then needs only the NVIDIA
driver and Docker with the NVIDIA container toolkit; the CUDA toolkit, Python and NumPy come from the image.

| Path in the image                 | What it is                                                                         |
| --------------------------------- | ---------------------------------------------------------------------------------- |
| `/opt/kiln/kiln_runner.py`        | the runner (`device`, `run`, `serve`), copied from `runner/`                       |
| `/opt/kiln/kiln_launch.py`        | the `kiln-program/1` launcher, copied from `runtime/python/`                       |
| `/opt/kiln/fixtures/`             | the launcher's five round-trip fixtures, generated by `runtime/test/fixtures.mjs`  |
| `/opt/kiln/kiln-probe.cu`         | the device probe (below)                                                           |
| `/usr/local/bin/kiln-selftest`    | the default command: the fixtures on this GPU, then the runner's device report     |
| `/usr/local/bin/kiln-probe`       | builds and runs the probe; prints a JSON report with a target spec                 |
| `/usr/local/cuda`                 | `nvcc`, NVRTC and the CUDA runtime from NVIDIA's apt repository (13.0 by default)  |

Base: `ubuntu:24.04`, for `amd64` and `arm64` (NVIDIA's `x86_64` and `sbsa` repositories). It is about 1.05 GB
unpacked and 356 MB compressed; `--ncu` adds Nsight Compute. The CUDA version must be one the host driver supports
(13.0 needs a 580-series driver).

## Build

```bash
runner/docker/build.sh                                  # here
runner/docker/build.sh --host manuel@bling.local        # on a GPU host, over SSH
runner/docker/build.sh --cuda 12.9 --ncu --tag kiln-perf:cuda12.9-ncu
runner/docker/build.sh --context-only /tmp/ctx          # stage the context and stop
```

`build.sh` stages the context (the two Python files, the probe, the scripts and freshly generated fixtures) and builds
it. The fixtures come from the compiler, so the default tag carries the Kiln revision, with `-dirty` when the runner,
launcher, fixture script, compiler or presets differ from `HEAD`. The image labels record the runner's and launcher's
SHA-256. With `--host`, the context is streamed as a tar and unpacked into a temporary directory on the host before
`docker build` runs there.

## Use

```bash
docker run --rm --gpus all kiln-perf:latest                     # self-test: 5 fixtures + device report
docker run --rm --gpus all --pid host --hostname "$(hostname)" kiln-perf:latest kiln-probe --id gb10
```

`kiln-probe` measures device-to-device copy, read and write bandwidth over 1 GiB buffers, the FP32 FMA rate, pinned
host transfers, and empty-kernel launch costs. It prints the probe's figures, the GPU's clocks, temperature and power
before and after, the compute processes sharing the GPU, and `spec`: the fields of
`packages/kiln/src/std/targets.js` `SPECS` with the measured figures (`peakTflops` the best FMA rate, `bwGBs` the
best read rate, `launchUs` an empty kernel between two CUDA events, as the runner times a kernel). Two flags matter:

- `--pid host`: inside the container's own PID namespace `nvidia-smi` cannot see other processes, so the list of
  co-tenants would be empty on a busy GPU. Without the flag the probe reports `computeApps: null` (unknown), not `[]`.
- `--hostname "$(hostname)"`: the report records the host name.

## As an executor's interpreter

`kiln-docker-python` runs the runner in the image instead of on the host. Copy it to the GPU host and point the
executor profile's `python` at its absolute path (the executor quotes the value, so `~` would not expand):

```json
{ "id": "spark", "target": "ssh", "host": "manuel@bling.local",
  "python": "/home/manuel/.local/bin/kiln-docker-python", "env": { "KILN_ARCH": "native" } }
```

The executor still copies its own runner to `~/.cache/kiln-runner/kiln_runner-<hash>.py`; the wrapper mounts that
directory at the same path, so the image supplies the toolchain and the executor supplies the runner. The wrapper
passes `--hostname` because the runner's device report, from which the device id is derived, includes the host name;
a container's random name would make the same GPU a new device on every probe. It runs with `--network none` and the
caller's uid, and keeps nvcc's build cache in `~/.cache/kiln-runner/build`. Each invocation costs a `docker run`
(0.1–0.5 s on a DGX Spark); kernel times are the same as on the host.

## Measured on a DGX Spark (GB10), 2026-10-20

Idle host (`bling`), three runs, `kiln-probe` medians (best in brackets):

| Figure                         | Value                     |
| ------------------------------ | ------------------------- |
| read bandwidth                 | 258.1 GB/s (259.2)        |
| device-to-device copy          | 240.9–243.1 GB/s          |
| write bandwidth                | 195.8 GB/s                |
| FP32 FMA                       | 28.92 TFLOP/s (28.93)     |
| pinned host to device, back    | 58.9 GB/s, 58.8 GB/s      |
| empty kernel between events    | 2.4 µs                    |
| launch + synchronise           | 4.9 µs                    |

Read bandwidth is 95 % of the 273 GB/s of 256-bit LPDDR5x at 8533 MT/s; the FMA rate is 98 % of 48 SMs × 128 lanes ×
2 flops at the 2.41 GHz `nvidia-smi` reports under load. These figures are the `gb10` entry in `SPECS`.
